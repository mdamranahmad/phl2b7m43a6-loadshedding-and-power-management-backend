# ⚡ Load Shedding & Power Outage Management System

A backend-only RESTful API for managing electricity distribution hierarchy (Zones → Substations → Feeders → Areas), planned load-shedding schedules, unexpected outage reporting, technician dispatch, and prepaid token recharge with real bKash payment integration.

Built as part of the **B7A6 Backend Project Assignment**.

## 🧭 Overview

Power distribution in this system flows through a fixed hierarchy:

```
Zone → Substation → Feeder → Area → House
```

- **Zone Managers** oversee multiple substations and approve escalated outage reports.
- **Substation Managers** allocate kW load, generate and publish load-shedding schedules, and assign technicians to outage reports.
- **Technicians** are dispatched to resolve outage reports and update resolution status.
- **Customers** manage their prepaid electricity tokens, view their zone's load-shedding schedule, and report unexpected outages.

The system distinguishes between **planned load shedding** (scheduled in advance, batch-generated by substation managers) and **unexpected outages** (customer-reported, triaged and assigned to technicians).

## 👥 User Roles

| Role | Description |
|---|---|
| `CUSTOMER` | End electricity consumer. Recharges tokens, views schedules, reports outages. |
| `TECHNICIAN` | Field staff. Applies for verification, receives assignments, resolves outage reports. |
| `SUBSTATION_MANAGER` | Manages a substation's kW allocation, generates/publishes schedules, reviews and assigns outage reports, approves technicians. |
| `ZONE_MANAGER` | Oversees all substations in a zone, reviews escalated outage reports, approves technicians. |

Roles are enforced via a `role`-aware `auth()` middleware that verifies the JWT, re-validates the user's live status in the database (blocked / soft-deleted / unverified users are rejected), and checks the caller's role against the route's allowed roles.

## 🔄 Core Workflow

**Planned Load Shedding**
```
Substation Manager allocates kW
   → generates schedule batch
   → publishes schedule batch
   → Customers view schedule for their zone
```

**Unexpected Outage**
```
Customer reports outage
   → Substation Manager reviews & assigns technician
   → Technician resolves (or reopens) the report
   → Zone Manager can review/approve escalated reports
```

**Prepaid Token Recharge**
```
Customer requests a token
   → bKash payment initiated
   → bKash callback verifies payment
   → Token marked PAID / Payment recorded
```

## 🚀 Getting Started

### Prerequisites

- Node.js 20+
- PostgreSQL database
- Redis instance
- A bKash sandbox/merchant account
- Cloudinary account
- SMTP credentials (e.g., Gmail App Password)

### Installation

```bash
# Clone the repository
git clone <your-repo-url>
cd <project-folder>

# Install dependencies
npm install

# Configure environment variables
cp .env.example .env   # then fill in the values (see below)

# Run database migrations
npx prisma migrate deploy

# Generate the Prisma client
npx prisma generate

# Start the development server
npm run dev
```

On first boot, `server.ts` automatically:
1. Connects to PostgreSQL
2. Seeds base **Zone** data
3. Seeds the default **Zone Manager**, **Substation Managers** (x2), and a **test Technician** account (from env credentials)
4. Connects to Redis
5. Starts the Express server

### Available Scripts

| Command | Description |
|---|---|
| `npm run dev` | Start the server in watch mode (`tsx watch`) |
| `npm run build` | Compile TypeScript to JavaScript |

## 🌱 Database Seeding

Seeding runs automatically on server start (`src/server.ts`) and is idempotent — it checks for existing records before creating new ones:

- **Zone data** — base zone required before any manager can be seeded
- **Zone Manager** — one account, tied to the seeded zone
- **Substation Managers** — up to two accounts, tied to their substations
- **Test Technician** — one pre-verified technician account for quick testing

Customer accounts are **not** seeded — register one via `POST /api/v1/auth/register`.

## 🚢 Deployment

The API is deployed on **Vercel** as a Node.js serverless function.

- **Live URL:** [https://phl2b7m43a6-loadshedding-and-power.vercel.app/](https://phl2b7m43a6-loadshedding-and-power.vercel.app/)
- `vercel.json` uses the legacy `builds`/`routes` config, pointing at the compiled `dist/server.js`:
  ```json
  {
      "version": 2,
      "builds": [{ "src": "dist/server.js", "use": "@vercel/node" }],
      "routes": [{ "src": "/(.*)", "dest": "dist/server.js" }]
  }
  ```
- All environment variables (see [Environment Variables](#-environment-variables)) must be configured in the Vercel project's **Settings → Environment Variables**, not read from a local `.env` file.
- `BACKEND_URL` and `BKASH_BASE_CALLBACK_URL` must point at the live Vercel domain (not `localhost`) for the bKash payment callback to work in production.
- Seeding (Zone, Zone Manager, Substation Managers, test Technician) runs on server start — for the hosted deployment this means the first cold start against a fresh database performs the seed automatically.

## 🧠 Key Engineering Decisions

- **Transaction-safe operations** — schedule batch generation, technician assignment, and token payment/recharge flows are wrapped in `prisma.$transaction()` to prevent race conditions (e.g., double-assigning a technician).
- **Soft deletes** — `isDeleted` / `deletedAt` fields on core models (User, Technician, Customer, OutageReport) instead of hard deletes.
- **Composite & lookup indexes** — e.g., `[reportStatus, isAssigned]` and `[zoneId, subStationId, areaId]` on `OutageReport` to keep the dispatch queries fast at scale.
- **Redis for short-lived state** — OTP codes, pending registration payloads, and bKash ID/refresh tokens are cached with TTLs rather than hitting Postgres or the bKash auth endpoint repeatedly.
- **Modular Prisma schema** — one `.prisma` file per domain model under `prisma/schema/`, composed together for readability and easier code review.

## 🧩 Known Limitations / Roadmap

- No dedicated `ADMIN` role — the `ZONE_MANAGER` role currently covers top-level oversight, and the `Role` enum has 4 values rather than 3.
- No audit log / activity-tracking model yet for critical actions (approvals, status changes).
- No global rate limiting or `helmet` security headers configured yet.
- No `POST /auth/logout` endpoint.
- Profile update endpoints (e.g., `PATCH /users/me`) are not yet implemented.
- Structured field-level validation errors (an `errors: []` array) are not yet returned — validation failures currently surface a single message string.
- Redis is currently used for OTP/token caching only, not for caching expensive read queries (schedules, analytics).
- `zonalManager`'s outage-report approval route is still `POST` rather than `PATCH`, inconsistent with the equivalent action in `subStationManager`.
